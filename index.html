Dejima

The substrate for multi-device agent workflows. pre-alpha

Dejima was an artificial island built in 1636 in Nagasaki Bay to serve as a quarantined trading post for foreigners during Japan's period of isolation.

Dejima is an OSS containment layer for AI coding agents. Each project runs in its own island: an isolated container with the target repo, the agent of your choice, and a brokered API that lets you drive the session from any device on your tailnet.

It is the interstitial layer between an agent and your machine. Not an interface. Not a product. Plumbing meant to be consumed by other applications — your CLI, a phone app, a Slack bot, a custom agent harness — all hitting the same API.

Install

curl -fsSL https://aoos.github.io/dejima/install.sh | bash

Runs on macOS and Linux. Bootstraps Go + Docker as needed, builds the binaries, installs them to /usr/local/bin, builds the island image, registers the daemon as a service, runs a health check. Idempotent — re-run to update.

What you get

  • Isolation — agents can't reach your host filesystem, other projects, or unrelated secrets.
  • Multi-project, multi-agent — N islands on one host, each its own repo and agent. No context bleed.
  • Persistent sessions — long-running work survives disconnects and host reboots via tmux + named volumes.
  • Multi-device attach — drive the same island from a laptop, phone, or web client. Shared screen, presence-aware.
  • Direct push to GitHub — host credentials mounted read-only into the island; git push just works.
  • API-first — the CLI is one client of the Dejima API. Mobile apps, Slack bots, custom integrations target the same surface.

Why Dejima?

Who it's for. Solo developers and small teams running AI coding agents on their own infrastructure — Mac mini, home server, VPS — who want project isolation and the ability to drive sessions from more than one device.

When to reach for it. When you're running agents on multiple repos in parallel, want to switch devices mid-task, or don't want unconstrained agent access to your laptop. Also: as a self-hosted alternative to vendor cloud agents.

The problem. Today's coding agents run on your laptop with full filesystem access, tied to one device and one project at a time. Vendor "remote control" features (Anthropic's, Replit's, etc.) lock you to a single agent on a single cloud. Per-project isolation is on you.

Why not just …?

AlternativeWhat's missing
Claude Code raw on your laptop Full filesystem access, no project isolation, tied to one device. Anthropic's remote-control feature is monitor-only and Claude-specific.
tmux + SSH Persistent sessions, yes — but no isolation, no per-project env, no API for other apps, no lifecycle verbs (hibernate / reset), no notifications. Dejima uses tmux inside each island; it doesn't replace tmux, it builds on it.
Vendor cloud (Devin, Replit Agent, etc.) Your data on someone else's hardware, vendor lock-in, one-agent-only, monthly bill.

Build on top

Most of the visible value should land on top of Dejima, not inside it. The Dejima API + webhook surface is meant to be the substrate for:

  • A mobile / PWA agent driver that works for any agent — better than vendor remote-control because cross-agent and self-hosted.
  • Chat-service integrations (dejima-slack, dejima-telegram) that drive sessions from a channel.
  • An agent manager that orchestrates many Dejima hosts (your Mac mini + a cloud VM + a friend's homelab) into one view.
  • Audit / compliance dashboards that consume the event stream.
  • Whatever else fits — Dejima is boring infrastructure on purpose so the interesting UX can live elsewhere.

Quickstart

# 1. Create an island around a real GitHub repo.
dejima init --repo git@github.com:you/myproject.git

# 2. Connect — drops you into Claude Code, inside the island.
dejima connect myproject

# 3. Disconnect with Ctrl-b then d (tmux). The session keeps running.

# 4. Pick up from another device on your tailnet:
DEJIMA_HOST=mac-mini.your-tailnet.ts.net:7273 dejima connect myproject

# 5. When memory pressure bites:
dejima hibernate myproject && dejima wake myproject

# 6. Fresh conversation, same code:
dejima reset myproject

# 7. When you're done:
dejima purge myproject

Concepts

TermMeaning
IslandThe container holding a single project and a single agent.
BridgeThe brokered I/O channel between host and island.

IntakeFiles passed into the island via dejima import.
Ledger(Post-v1) An audit log of every bridge transaction.

dejima statusDetail view of one island, including presence + resource use.
dejima hibernateStop the container, preserve volumes.
dejima wakeStart a hibernated island.
dejima resetClear agent state. Preserves workspace.

dejima cpCopy files in or out of an island.
dejima logsTail an island's container logs (--follow).
dejima doctorHealth check: daemon, Docker, image, projects, webhooks.
dejima serviceInstall / uninstall dejimad as a host service.
dejima webhookSubscribe a URL to receive state-change events.
dejima purgeDestroy island and volumes.

Webhooks

Get notified when an agent finishes a task or needs your input:

dejima webhook subscribe --url https://ntfy.sh/your-private-topic

Events include lifecycle (island.hibernated, island.woken, …), presence (client.attached, client.detached), and — when the Claude Code shim is active — agent.waiting-for-input and agent.task-complete. This is the integration point for Slack / Discord / Telegram bots, mobile push, custom dashboards. Dejima stays agnostic about what's on the other end.
